# 2026-W47 — beta date set, first real checks: email and websites

Covers 16-21 November 2026.

## What was built
- **Roadmap for a downloadable beta** (17 November, PR #3): beta 0.1 on 1 December 2026, with single-file executables for Windows, Linux and macOS and SHA-256 hashes. Packaging moves forward from v1.0. Dated checkpoints on 20/11, 27/11 and 29/11; v1.0 by 15 December at the latest.
- **Review of the work so far** (19 November) before starting v0.1. The code of v0.0 held up: build and 174 tests green, no defects found in the Core contracts. The problems were in the plan:
  - no v0.1 work had started since 15 November, so checkpoint 1 (20/11) will be missed for websites;
  - the `scudo scan` command line is part of v0.1 but no worktree owns it;
  - the email area listed 7 checks; the beta keeps 4 topics (SPF, DMARC, DKIM, MX) and moves MTA-STS, DNSSEC, STARTTLS, DNSBL and BIMI after it.
- **`Checks.Email`, the first module with real checks** (19 November, branch `feature/v0.1-email`): 11 passive checks on a domain, using only the public DNS:
  - SPF: record present and unique, final `all` (following `redirect=`), the limit of 10 DNS lookups with includes followed recursively, invalid terms, broken includes, loops, `ptr`;
  - DMARC: missing, invalid, `p=none`, `pct` below 100, no aggregate reports, `sp=none`; a subdomain without its own record inherits the parent's policy;
  - DKIM: 29 common selectors (including those of OVHcloud) plus the user's own, key length read from the key itself (RSA < 1024 bits High, < 2048 Medium), test mode;
  - MX: missing, null MX, hosts without an address, MX pointing to an IP address.
  - Every finding has a title, a risk and a fix in English and Italian, and the RFC it refers to.

- **`scudo scan --mail <domain>`** (19 November, branch `feature/v0.1-cli-scan`): the first command that does something. It prints the banner, the warning and who declared the assessment, runs the email checks and lists the problems most urgent first, with evidence, risk and fix, in Italian on an Italian system. Active checks are refused until ownership can be proven (v0.2). Text only for now: HTML and PDF come with the reports.

- **`Checks.Web`, first pass, and `scudo scan --web <domain>`** (21 November, branch `feature/v0.1-web`): 15 passive checks on a website, one per kind of problem as for email:
  - HTTPS: the site answers over HTTPS, and plain HTTP redirects there at the first step;
  - certificate: expiry (expired, fewer than 14 days, at most 30), chain (unknown authority, issuer not sent), name;
  - HSTS, Content-Security-Policy (missing, report-only, or one that does not limit scripts), protection from clickjacking, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`;
  - cookies without `Secure`, `HttpOnly`, `SameSite`, one finding per cookie, never showing the value;
  - `security.txt` (missing, without contact, expired).
  - A visit is four requests at most: the home page over HTTP and over HTTPS, and `security.txt` at its two standard addresses. Redirects are followed only inside the declared domain. The certificate is read from the same connection; missing intermediate certificates are not downloaded and revocation is not asked, because both would be connections to servers nobody declared. The report says that revocation is not checked.
  - `--mail` and `--web` work together, also on the same domain: two sections, each area on its own target.
  - Left for a second pass, on purpose: TLS versions and ciphers (what a client can offer depends on the operating system, so it needs a decision first), CMS detection, indicative GDPR.

## What broke and how it was fixed
- **A test found a hang before the code ever ran on a real network.** The fake DNS used in the tests can hang forever and ignore cancellation, as a broken resolver would. With it, the MX check waited forever: it awaited the resolver without enforcing its own deadline. Fixed with `WaitAsync(token)`; the test now has a timeout, so the same mistake turns it red instead of blocking the suite.
- **The home router could not keep up.** On the first real run `example.com` took 50 seconds, close to the 60-second limit of a check. Measured step by step:
  - the router dropped many TXT queries;
  - EDNS (large UDP answers) was not the cause: the same losses with and without it;
  - 8 queries in flight at once made things much worse than 1;
  - my first comparison with the Windows resolver was wrong, because its answers came from the Windows cache (27-74 ms).
  Fixed by keeping the cautious default of 4 queries in flight (I had raised it to 8), and using a 2-second timeout with one retry instead of 3 seconds. When the resolver does not answer, the checks now fail with the DNS error, and the DKIM check lists the selectors that got no answer. Before, "no DKIM key found" could hide a query that never got an answer. The 27 DKIM queries also share a 25-second budget: in the worst case they would have taken 56 seconds, and a check that hits the 60-second limit tells the user nothing.
- **The router also intercepted public DNS.** Decided with the author: ask Cloudflare and Google instead of the router. Sending plain DNS to 1.1.1.1 and 8.8.8.8 did not work either: answers came back in 12 ms with "refused" or with the wrong query id, so something on the way was answering in their place. DNS over HTTPS (port 443, encrypted) reached them at once. The checks now ask Cloudflare and then Google over HTTPS, with the computer's DNS as a last resort. Every test domain now takes 0.4-1.3 seconds instead of up to 50.
- **My counter-check script lied, again.** The first full run said that 44 of 45 deliberate bugs went unnoticed. In fact the test project did not compile, because the timeouts I had just added break an xUnit rule (a test with a timeout must use the test's cancellation token), and the script only looked for C# compiler errors. Stopping the script halfway also left one deliberate bug in the code; the test with the new timeout caught it. Fixed the tests, made the script treat any build error as "no result", and ran every counter-check again.
- **Green on Windows, red on Linux and macOS.** A CLI test expected the date "11/19/2026 10:30 AM". On Linux and macOS, .NET formats dates with ICU, which puts a narrow no-break space (U+202F) before "AM". The test now asks the platform for the expected format.
- **The tool was wrong about my own domain, and said so honestly.** It reported "no DKIM key found on the common selectors" for `gcardinale.it`, marked "to be verified". Checking in the OVHcloud panel: DKIM was active all along, with OVH's own selectors `ovhmo-selector-1` and `ovhmo-selector-2`, which were not in the list. The "to be verified" label was the right call; the list was too short. Both selectors are now common ones, since many Italian domains use OVHcloud. The real problem was DMARC in monitoring mode: changed from `p=none` to `p=quarantine` the same day, after checking that DKIM signs the mail.
- **Two of my test expectations were wrong, not the code**: the punycode of `caffè.it` is `xn--caff-8oa.it`, and a trailing newline is removed on purpose, as `Target` in Core already does.
- **Websites: little broke, and the reasons are worth writing down.** The first real run on `gcardinale.it` worked at the first attempt. What went wrong was found earlier, while writing:
  - a response without a `Content-Type` would have been read as a page, because "no type expected" and "no type sent" compared as equal: found rereading the code, before any test;
  - .NET on Windows stores intermediate certificates in the user's certificate store when a test server is given a chain to send. The test authority would have ended up installed on the developer's computer. The tests now never hand a chain to the server: the "issuer not sent" case uses a certificate whose issuer simply is not there. Checked afterwards: nothing in the stores;
  - the same xUnit rule as last week (a test with a timeout must use the test's cancellation token) stopped the build once more;
  - a cookie named `csrftoken` was treated as a session cookie because of "token" in its name: anti-forgery tokens are meant to be read by the page, so they are now left out.
- **Deliberate bugs.** 49 bugs put into the code one at a time (a `<` turned into `<=`, a check removed, a redirect followed outside the domain): 47 turned a test red. The two that stayed green each said something. One: nothing proved that four checks starting together on different threads share one visit instead of making four; a test now does. Two: the command line removed duplicate sites that the scope declaration in Core already removes; the extra line is gone. The same run also showed that an unreachable site was reported as "No problems found" above fifteen checks that could not run: that sentence is now printed only when something was actually checked (it applies to `--mail` too).
- **The tool found two things on my own site**: a Content-Security-Policy that allows inline scripts (Low) and no `security.txt` (Info). Both true. Not fixed yet.
- **A second pair of eyes, the same day.** The website checks were merged before anyone but their author had read them, so an independent review followed straight after. It found no crash, and these, all confirmed and fixed with a test each:
  - a slow page was reported as "the site does not answer over HTTPS", High and certain. The headers had arrived; only the body was late. The answer is now kept, and "no HTTPS" is certain only when the connection is refused; any other failure is "to be verified";
  - a session identifier could reach the report by two roads: in an address (`;jsessionid=…`, which some servers add exactly because no cookie is sent back), and when a proxy joins two cookies in one header line. Addresses are now shown without parameters and query, cookies are told apart and their attributes shown by name only. Writing the test for this fix found a third case in the fix itself;
  - `nosniff, nosniff` was called wrong (browsers read the first value), `frame-ancestors *` counted as protection, a redirect could send a request to any port of the site, an unreadable certificate would have looked like "no HTTPS".
  - Not fixed, written down as limits in `features/Checks.Web/status.md`: the system proxy is used; on Windows an incomplete chain goes unnoticed when Windows already knows the missing certificate; Windows may download a root certificate by itself.
- **After the review, three decisions of the author, the same day.** The DNS of the home router had already failed once for websites ("unknown host" on a name that exists), so the resolver built for email moved to `Core` and the website checks now ask it for the address of the site: Cloudflare and Google over HTTPS, then the DNS of the computer. The address is asked once per site and before the requests. With `--system-dns` the name is left to the operating system: asking the router directly gave "Server Failure" on a name that exists. The system proxy stays, because where a proxy is mandatory nothing works without it, but the report now says when a site is reached through one, and that a proxy inspecting encrypted traffic shows its own certificate. `X-Frame-Options` with a value browsers ignore went from Low to Medium: it protects as little as no header.
- **A second review, on the shared resolver, found three defects of mine.** Only the name typed by the user was resolved in advance: the name of a redirect (`example.com` to `www.example.com`) was resolved inside the 10 seconds of the connection, so a slow resolver produced a false "HTTPS unusable". A name of the local network was reported as non-existent, because Cloudflare does not know it. And two connections waiting for the same name shared a question that the first one could cancel for both. Now every name is resolved before its request, the question belongs to the fetcher, and the operating system is asked when the public resolvers have no address. The author chose to keep the public resolvers first, as for email.
- **A new test found what the review had not.** Written to prove that nothing is asked to the resolver behind a proxy, it failed: .NET opens the tunnel towards an HTTPS site with a CONNECT request addressed to the proxy, my code took it for a direct connection, and the name of the proxy went to Cloudflare. One line to fix, and the test stays.
- **A third review, on those fixes, found that I had opened a new hole while closing one.** Asking the operating system about a name the public DNS does not know is right for an intranet site, but many providers and routers answer a name that does not exist with the address of their own search page: a mistyped domain would have been checked there, with findings marked as certain, on a server nobody declared. Now, after "does not exist", only a local or private address is believed. The same review showed that with a proxy for HTTPS only the plain address was still resolved late, and that a redirect to a name no DNS answered for was reported as "HTTPS unusable": it is now "could not run".

## Decisions taken
- [ADR-006 — One check per kind of problem, and DNS through public resolvers over HTTPS](../decisions/ADR-006-check-granularity-and-dns-for-email.md) (accepted). Every id has one risk and one fix text, so the comparison between two reports can tell that a problem changed. DNS goes to Cloudflare and Google over HTTPS, which see only the public domain names checked.
- Websites follow ADR-004 (passive on any target) and ADR-006 (one check per kind of problem) with no new ADR. Decided with the author on 21 November: redirects only inside the declared domain; the DNS of the computer for websites (changed the same day after it failed once: websites now use the DNS over HTTPS resolver too, see the addition at the end of ADR-006); a declared user agent; severities as in `features/Checks.Web/status.md`. TLS versions and ciphers will need ADR-007.

## Real domains
- Run on 19 November through the real engine, on the author's domain, on `example.com` (the IANA test domain) and on a domain that does not exist. Same results on the first run and on the last one, after all the fixes; `gcardinale.it` took 0.6 seconds.
  - `gcardinale.it`: SPF ok (`include:mx.ovh.com -all`), DMARC in monitoring mode (`p=none`, Medium), no DKIM key on the common selectors (to be verified), two `ptr` mechanisms found inside OVH's include (Low, the provider's record).
  - `example.com`: SPF `-all`, DMARC `p=reject`, null MX; the only findings are no `rua` (Low) and no DKIM key (to be verified), both expected for a domain that sends no mail. On some runs the home router did not answer for the DKIM selectors of `example.com`: the check then said so, or failed with the DNS error, instead of claiming there was no key.
  - `microsoft.com`, after the switch to DNS over HTTPS: first real problem found on someone else's domain — a 1024-bit DKIM key on selector `selector2` (Medium, below the recommended 2048 bits).
  - `non-esiste-davvero-1234.it`: every check fails with "the domain does not exist in the public DNS", in Italian on an Italian system.
- Websites, run on 21 November with `scudo scan --web`, in Italian on an Italian system; each site took 1 to 9 seconds:
  - `gcardinale.it`: 10 checks passed (HTTPS, redirect, certificate, HSTS, clickjacking, `nosniff`, `Referrer-Policy`, `Permissions-Policy`); a Content-Security-Policy that allows inline scripts (Low) and no `security.txt` (Info); no cookies on a first visit, so the three cookie checks are skipped and say so.
  - `example.com`: served over HTTP without a redirect (Medium), no HSTS, no Content-Security-Policy, no clickjacking protection (Medium each), plus the Low and Info headers. Certificate fine.
  - The test sites of badssl.com, each built with one certificate problem: `expired.badssl.com` → certificate expired (High, valid until 12/04/2015); `self-signed.badssl.com` → not issued by a recognized authority (High); `wrong.host.badssl.com` → the certificate does not cover the name (High, issued for `*.badssl.com`); `incomplete-chain.badssl.com` → incomplete chain (Medium, probable). The last one is found only because missing certificates are not downloaded: a browser on Windows fetches the missing one and shows nothing.
  - `non-esiste-davvero-1234.it`: every check fails with "the site cannot be reached: unknown host", and the report no longer says "no problems found" above a list of checks that could not run.
