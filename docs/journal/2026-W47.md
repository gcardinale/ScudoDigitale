- **`Checks.Email`, the first module with real checks** (19 November, branch `feature/v0.1-email`): 11 passive checks on a domain, using only the public DNS:
  - SPF: record present and unique, final `all` (following `redirect=`), the limit of 10 DNS lookups with includes followed recursively, invalid terms, broken includes, loops, `ptr`;
  - DMARC: missing, invalid, `p=none`, `pct` below 100, no aggregate reports, `sp=none`; a subdomain without its own record inherits the parent's policy;
  - DKIM: 27 common selectors plus the user's own, key length read from the key itself (RSA < 1024 bits High, < 2048 Medium), test mode;
  - MX: missing, null MX, hosts without an address, MX pointing to an IP address.
  - Every finding has a title, a risk and a fix in English and Italian, and the RFC it refers to.

- **`scudo scan --mail <domain>`** (19 November, branch `feature/v0.1-cli-scan`): the first command that does something. It prints the banner, the warning and who declared the assessment, runs the email checks and lists the problems most urgent first, with evidence, risk and fix, in Italian on an Italian system. Active checks are refused until ownership can be proven (v0.2). Text only for now: HTML and PDF come with the reports.

## What broke and how it was fixed
- **A test found a hang before the code ever ran on a real network.** The fake DNS used in the tests can hang forever and ignore cancellation, as a broken resolver would. With it, the MX check waited forever: it awaited the resolver without enforcing its own deadline. Fixed with `WaitAsync(token)`; the test now has a timeout, so the same mistake turns it red instead of blocking the suite.
- **The home router could not keep up.** On the first real run `example.com` took 50 seconds, close to the 60-second limit of a check. Measured step by step:
  - the router dropped many TXT queries;
  - EDNS (large UDP answers) was not the cause: the same losses with and without it;
  - 8 queries in flight at once made things much worse than 1;
  - my first comparison with the Windows resolver was wrong, because its answers came from the Windows cache (27-74 ms).
  Fixed by keeping the cautious default of 4 queries in flight (I had raised it to 8), and using a 2-second timeout with one retry instead of 3 seconds. When the resolver does not answer, the checks now fail with the DNS error, and the DKIM check lists the selectors that got no answer. Before, "no DKIM key found" could hide a query that never got an answer. The 27 DKIM queries also share a 25-second budget: in the worst case they would have taken 56 seconds, and a check that hits the 60-second limit tells the user nothing.
- **The router also intercepted public DNS.** Decided with the author: ask Cloudflare and Google instead of the router. Sending plain DNS to 1.1.1.1 and 8.8.8.8 did not work either: answers came back in 12 ms with "refused" or with the wrong query id, so something on the way was answering in their place. DNS over HTTPS (port 443, encrypted) reached them at once. The checks now ask Cloudflare and then Google over HTTPS, with the computer's DNS as a last resort. Every test domain now takes 0.4-1.3 seconds instead of up to 50.
- **My counter-check script lied, again.** The first full run said that 44 of 45 deliberate bugs went unnoticed. In fact the test project did not compile, because the timeouts I had just added break an xUnit rule (a test with a timeout must use the test's cancellation token), and the script only looked for C# compiler errors. Stopping the script halfway also left one deliberate bug in the code; the test with the new timeout caught it. Fixed the tests, made the script treat any build error as "no result", and ran every counter-check again.
- **Green on Windows, red on Linux and macOS.** A CLI test expected the date "11/19/2026 10:30 AM". On Linux and macOS, .NET formats dates with ICU, which puts a narrow no-break space (U+202F) before "AM". The test now asks the platform for the expected format.
- **Two of my test expectations were wrong, not the code**: the punycode of `caffè.it` is `xn--caff-8oa.it`, and a trailing newline is removed on purpose, as `Target` in Core already does.

## Decisions taken
- [ADR-006 — One check per kind of problem, and DNS through public resolvers over HTTPS](../decisions/ADR-006-check-granularity-and-dns-for-email.md) (accepted). ## Real domains
- Run on 19 November through the real engine, on the author's domain, on `example.com` (the IANA test domain) and on a domain that does not exist. Same results on the first run and on the last one, after all the fixes; `gcardinale.it` took 0.6 seconds.
  - `gcardinale.it`: SPF ok (`include:mx.ovh.com -all`), DMARC in monitoring mode (`p=none`, Medium), no DKIM key on the common selectors (to be verified), two `ptr` mechanisms found inside OVH's include (Low, the provider's record).
  - `example.com`: SPF `-all`, DMARC `p=reject`, null MX; the only findings are no `rua` (Low) and no DKIM key (to be verified), both expected for a domain that sends no mail. On some runs the home router did not answer for the DKIM selectors of `example.com`: the check then said so, or failed with the DNS error, instead of claiming there was no key.
  - `microsoft.com`, after the switch to DNS over HTTPS: first real problem found on someone else's domain — a 1024-bit DKIM key on selector `selector2` (Medium, below the recommended 2048 bits).
  - `non-esiste-davvero-1234.it`: every check fails with "the domain does not exist in the public DNS", in Italian on an Italian system.
